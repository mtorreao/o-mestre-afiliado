## 🔴 [CRÍTICA] #1 — Rotas ML sem nenhuma autenticação ✅ CORRIGIDO

**Arquivo:** `apps/api/src/modules/ml/ml.routes.ts`  
**Status:** ✅ Corrigido em 2026-08-01

As seguintes rotas **não tinham middleware JWT nem verificação de auth**:

| Método   | Rota                                            | Risco                                                           |
| -------- | ----------------------------------------------- | --------------------------------------------------------------- |
| `PUT`    | `/api/ml/affiliates/:mlUserId`                  | Sobrescrever sessionCookies/meliid/melitat de qualquer afiliado |
| `DELETE` | `/api/ml/affiliates/:mlUserId`                  | Deletar qualquer afiliado                                       |
| `POST`   | `/api/ml/convert`                               | Uso indevido de credenciais de afiliados alheios                |
| `POST`   | `/api/ml/refresh`                               | Refresh de token OAuth de terceiros                             |
| `POST`   | `/api/ml/affiliates/:mlUserId/validate-cookies` | Testar cookies de sessão de qualquer afiliado                   |
| `GET`    | `/api/ml/affiliates`                            | Listar TODOS os afiliados com tokens e cookies visíveis         |

**Correção aplicada:**

- Adicionado `.use(createJwtPlugin())` no módulo
- Todas as rotas agora exigem autenticação JWT
- Verificação de ownership: `affiliate.userId === auth.userId`
- Listagem filtra por `userId: auth.userId` (admin vê todos)
- Rotas OAuth (`/api/ml/auth` e `/api/ml/callback`) mantidas públicas por design

**Testes:** ✅ 462 testes passaram, 0 regressões

## 🔴 [CRÍTICA] #3 — Webhook sem autenticação ✅ CORRIGIDO

**Arquivo:** `apps/api/src/modules/webhook/webhook.routes.ts`
**Status:** ✅ Corrigido em 2026-08-01

A variável `EVOLUTION_API_KEY` era lida (linha 28) mas **nunca verificada** no handler. Qualquer pessoa podia enviar `POST /webhook/message` e:

- Injetar mensagens falsas na Queue A do pipeline de espelhamento
- Alterar status de conexões WhatsApp de qualquer usuário
- Invalidar caches de grupo

**Correção aplicada:**

- Validação constant-time do header `apikey` contra `EVOLUTION_API_KEY` usando `safeEqual()`
- Retorna 503 se `EVOLUTION_API_KEY` não estiver configurada (fail-closed)
- Retorna 401 se apikey for inválida ou ausente
- Proteção contra timing attacks

**Testes:** ✅ 462 testes passaram, 0 regressões

## 🔴 [CRÍTICA] #4 — JWT Secret hardcoded como fallback ✅ CORRIGIDO

**Arquivo:** `apps/api/src/middleware/auth.ts`
**Status:** ✅ Corrigido em 2026-08-01

O fallback hardcoded `'omestre-dev-secret-change-in-production'` foi removido. Agora:

- **Produção:** lança erro se `JWT_SECRET` não estiver configurado (fail-closed)
- **Desenvolvimento:** gera secret aleatório via `crypto.randomUUID()` com aviso no console
- Tokens de dev não sobrevivem restarts (intencional para segurança)

**Correção aplicada:**

```typescript
function getJwtSecret(): string {
  if (config.JWT_SECRET) return config.JWT_SECRET;

  const isDev = process.env.NODE_ENV !== 'production';
  if (!isDev) {
    throw new Error('JWT_SECRET is required in production');
  }

  const devSecret = crypto.randomUUID();
  console.warn('[SECURITY WARNING] JWT_SECRET not set. Using random dev secret.');
  return devSecret;
}
```

**Testes:** ✅ 462 testes passaram, 0 regressões

## 🟠 [ALTA] #5 — CORS completamente aberto

**Arquivo:** `apps/api/src/index.ts:40`

```typescript
.use(cors())
```

Sem configuração = permite qualquer origin. Em produção, qualquer site pode fazer requests autenticados. Embora o frontend use Bearer token (não cookies), CORS aberto permite:

- Data exfiltration via JavaScript de terceiros se o token vazar
- Enumeração de endpoints e fingerprinting da API

**Correção sugerida:**

```typescript
.use(cors({
  origin: [config.FRONTEND_URL],
  methods: ['GET', 'POST', 'PUT', 'PATCH', 'DELETE'],
}))
```

## 🟠 [ALTA] #6 — JWT sem expiração

**Arquivo:** `apps/api/src/middleware/auth.ts:32-36`

O schema do JWT não inclui `exp`. Tokens **nunca expiram**. Se um token vazar, o atacante tem acesso permanente até que o secret seja trocado.

**Correção sugerida:**

```typescript
const token = await jwt.sign({
  userId: user.id,
  userEmail: user.email,
  isAdmin,
  exp: Math.floor(Date.now() / 1000) + 7 * 24 * 60 * 60, // 7 dias
});
```

Adicionar `exp` ao schema e revalidar no login/refresh.

## 🟠 [ALTA] #7 — Sem rate limit em login/register

**Arquivo:** `apps/api/src/modules/auth/auth.routes.ts`

| Rota                      | Linha | Problema                                   |
| ------------------------- | ----- | ------------------------------------------ |
| `POST /api/auth/register` | 14    | Sem rate limit — criação massiva de contas |
| `POST /api/auth/login`    | 59    | Sem rate limit — brute force de senhas     |

Só a extensão Chrome tem rate limit (`extension-log.routes.ts`).

**Correção sugerida:**

- Rate limit por IP: 5 tentativas de login por minuto, 3 registros por hora.
- Bloquear IP após N falhas consecutivas.

## 🟡 [MÉDIA] #10 — SSRF em ML convert (meli.la resolver)

**Arquivo:** `apps/api/src/modules/ml/ml.routes.ts:302`

```typescript
const resolved = await fetch(url, { method: 'HEAD', redirect: 'manual' });
```

O URL vem direto do body do usuário. Se o atacante enviar `http://169.254.169.254/latest/meta-data/` (AWS metadata) ou `http://localhost:5443/` (PostgreSQL), o servidor faz o request. Sem allowlist de domínios.

**Correção sugerida:**

- Validar que a URL pertence a `mercadolivre.com.br`, `mercadolibre.com`, ou `meli.la` antes de fazer fetch.

## 🟡 [MÉDIA] #11 — OAuth state sem CSRF protection

**Arquivo:** `apps/api/src/modules/ml/ml.routes.ts:39`

```typescript
const state = (query as { userId?: string }).userId || '';
```

O parâmetro `state` do OAuth é apenas o `userId` em plain text. Sem nonce aleatório, sem HMAC. Um atacante pode forjar o callback e vincular uma conta ML arbitrária a qualquer `userId`.

**Correção sugerida:**

- Gerar nonce aleatório + HMAC do userId.
- Validar no callback.
- Armazenar nonce em Redis com TTL curto (5 min).
